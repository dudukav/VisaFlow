# VisaFlow Engineering Guidelines

**Статус:** живой стандарт команды  
**Область:** Go backend, React/TypeScript clients, Python Document Processor  
**Связанные документы:** [PRD](PRD.md), [SRS](SRS.md), [C4 context](diagrams/c4-context.puml)

Документ фиксирует выбранный дизайн системы, обязательные соглашения по коду и критерии готовности изменений. Это рабочий стандарт, а не исчерпывающее описание паттернов.

## 1. Дизайн системы

VisaFlow строится как **модульный монолит с доменно-ориентированными модулями и слоями внутри модулей**. Полный tactical DDD не применяется: доменные типы и паттерны нужны только там, где есть реальные бизнес-инварианты.

- React + TypeScript: Telegram Mini App и Admin UI.
- Go core: HTTP API, бизнес-логика и фоновые процессы.
- Python Document Processor: изолированные file validation, malware scan, OCR и normalization.
- PostgreSQL: единственный источник бизнес-состояния.
- Redis: доставка jobs, но не источник истины.
- S3-compatible storage: бинарные документы.
- Telegram и визовые порталы: внешние системы за адаптерами.

Document Processor выделен из-за отдельного профиля безопасности, ресурсов и зависимостей. Остальные возможности остаются в монолите, пока для выделения сервиса нет измеримой причины: отдельного SLA, security boundary, профиля масштабирования, release cadence или команды.

## 2. Модули и зависимости

Go core разделяется по бизнес-возможностям:

`identity`, `application`, `rules`, `checklist`, `documents`, `deadlines`, `notifications`, `appointments`, `billing`, `admin`, `audit`.

```text
transport ─┐
           ├─> application ─> domain
adapters ──┘
```

Обязательные правила:

1. Модуль владеет своими моделями, таблицами и правилами.
2. Другие модули используют его application API; прямой доступ к внутренним пакетам и таблицам запрещён.
3. `domain` не зависит от framework, БД, сети и файловой системы.
4. `application` координирует use cases и транзакции и объявляет нужные ему порты.
5. `transport` только валидирует внешний контракт, вызывает use case и преобразует результат.
6. PostgreSQL, Redis, S3, Telegram и порталы подключаются через adapters.
7. Consumers идемпотентны; надёжная публикация jobs после изменения state выполняется через transactional outbox.

Рекомендуемая, но не обязательная для простого CRUD структура:

```text
internal/<module>/
  domain/
  application/
  adapters/
  transport/
```

Пустые слои, интерфейсы «на будущее» и симметрия ради шаблона не создаются.

## 3. Общий code style

- Имена описывают предметную роль; избегаем `Data`, `Manager`, `Helper`, `Utils`, `Process`.
- Функция решает одну связанную задачу. Смешение вычислений и I/O, глубокая вложенность и несколько причин изменения требуют разделения.
- Комментарии объясняют причину или ограничение, а не пересказывают код.
- Абстракция появляется при реальной вариативности или границе; простое локальное дублирование допустимее неверной абстракции.
- Запрещены скрытый global state, service locator и изменяемые package-level variables.
- Внешний input валидируется на границе; transport DTO не становится доменной моделью.
- Жизненный цикл моделируется явным status и проверяемыми переходами.
- Время хранится в UTC; IDs, timestamps и idempotency keys передаются явно.
- Ошибки содержат контекст операции, но не PII, secrets, исходные имена файлов или полный OCR.
- API и job contracts версионируются при несовместимых изменениях.

## 4. Языковые соглашения

### Go

- Обязательны `gofmt`, `goimports`, `go vet`, `golangci-lint`.
- `context.Context` — первый аргумент I/O-операции и не хранится в struct.
- Ошибки оборачиваются через `%w` и проверяются через `errors.Is/As`, не по тексту.
- Интерфейс объявляется на стороне потребителя и остаётся минимальным.
- `panic` не используется для пользовательского input и штатных отказов зависимостей.
- Каждая goroutine имеет владельца, cancellation и обработку ошибки.
- Обязательные зависимости передаются явно через конструктор.

### TypeScript / React

- Включён `strict`; `any` допустим только как документированный interop на внешней границе.
- Ответ API валидируется до преобразования во внутренний тип.
- UI не дублирует бизнес-правила backend.
- Server state отделён от local UI state; effects используются для синхронизации, не для вычисления производного state.
- Обязательны formatter, `eslint`, type-check и production build.

### Python Document Processor

- Обязательны `ruff`, type hints на публичных границах, `mypy` и `pytest`.
- OCR/normalization отделены от скачивания, filesystem и callback API.
- Временные файлы удаляются при успехе, ошибке и timeout.
- Processor не содержит визовых правил и не имеет прямого доступа к PostgreSQL.
- Недоверенный файл не может определять shell command, произвольный путь или outbound URL.

## 5. Тестирование

- Domain tests покрывают бизнес-инварианты, переходы состояний и граничные случаи.
- Application tests проверяют use case, отказы зависимостей и повтор операции через ports.
- Adapter integration tests проверяют реальный протокол или совместимый test container.
- Contract tests фиксируют OpenAPI, job payload и внешние adapters.
- E2E покрывает критические пути: auth, application/checklist, document flow, deletion и notification.
- Исправление дефекта сопровождается воспроизводящим тестом, если это технически возможно.
- Глобальный процент coverage не является целью; существенные ветви нового бизнес-кода должны быть протестированы.
- В development, CI и demo используются только синтетические fixtures без PII.

## 6. Definition of Done

Изменение готово к merge, когда:

- соответствует требованию или явно описанному сценарию;
- сохраняет границы модулей и направление зависимостей;
- проходит format, lint, type-check/build и тесты затронутых компонентов;
- новые правила, state transitions и error paths покрыты тестами;
- migration совместима с предыдущей версией на время rollout;
- повтор job/callback не повреждает state, если требуется идемпотентность;
- проверены authorization, PII и содержимое logs;
- внешние операции имеют timeout, cancellation и классификацию ошибок;
- API/job contract и эксплуатационно значимые изменения отражены в документации;
- reviewer может проследить основной поток без скрытых соглашений автора.

## 7. Автоматизация

После появления кода CI предоставляет единые команды `make fmt`, `make lint`, `make test`, `make build`. Правило считается обязательным, но автоматизированным — только после добавления соответствующей проверки в CI.

Исключение из документа допускается в pull request, если описаны причина, риск и срок устранения. Повторяющееся исключение означает, что нужно изменить код или сам стандарт.
