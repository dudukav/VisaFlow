## 1. Введение

### 1.1 Назначение документа

Документ описывает, **что именно должна делать** система VisaFlow в MVP и по каким наблюдаемым критериям требования принимаются. Он служит общей опорой для разработки, тестирования, архитектуры и RTM.

### 1.2 Область (scope)

**Входит в MVP:**

- Telegram-аутентификация и роли Applicant/Administrator;
- туристические визы Италии, Испании и Японии;
- заявка с основным заявителем и членами семьи;
- версионированные правила, персональный checklist, сроки и напоминания;
- безопасная загрузка синтетических документов, локальный OCR и rule-based проверка;
- проверенные официальные ссылки на запись;
- экспериментальный мониторинг Италии за feature flag;
- админка, аудит, retention и тестовый сценарий оплаты.

**Не входит в MVP:**

- национальные, рабочие, учебные и иммиграционные визы;
- полностью автоматическое бронирование и обход защит порталов;
- юридическая консультация и прогноз решения консульства;
- реальные платежи, ККТ и фискальные чеки;
- реальные документы в development, CI и учебной демонстрации.

### 1.3 Термины и сокращения

- **Applicant** — владелец заявки и Telegram-профиля.
- **Family member** — участник поездки внутри заявки; отдельный аккаунт в MVP не обязателен.
- **Administrator** — роль, публикующая правила и контролирующая технические статусы.
- **Ruleset** — неизменяемая после публикации версия правил для страны, типа визы и юрисдикции.
- **Checklist** — набор действий и документов, рассчитанный для конкретной заявки и ruleset.
- **OCR** — локальное распознавание полей документа.
- **Signed URL** — временная ссылка, ограниченная операцией над одним объектом.
- **Capability** — объявленная возможность адаптера: official link, monitoring или unsupported.
- **FR / NFR** — функциональное / нефункциональное требование.

## 2. Общее описание

### 2.1 Контекст и место в продукте

Основной клиент — Telegram Mini App. React-клиент обращается к Go API; фоновые Go workers обрабатывают сроки, уведомления и адаптеры; отдельный локальный Python worker выполняет OCR. PostgreSQL хранит доменные данные, Redis — идемпотентные задания, S3-compatible storage — файлы. Внешние стороны: Telegram Bot API и официальные визовые источники.

### 2.2 Пользователи

- **Applicant:** создаёт заявку, добавляет семью, выполняет checklist, загружает и удаляет документы, получает уведомления.
- **Family member:** сущность участника внутри заявки; действия выполняет владелец заявки.
- **Administrator:** создаёт draft правил, проверяет diff, публикует ruleset, управляет feature flags и видит health без доступа к содержимому документов по умолчанию.

### 2.3 Допущения и зависимости

- Mini App запускается из поддерживаемой версии Telegram и получает `initData`.
- Для каждой страны существует вручную проверенный официальный URL.
- Набор правил подготовлен и опубликован Administrator до создания checklist.
- OCR поддерживает только заранее определённые типы синтетических документов.
- Экспериментальный Italy adapter запускается только после проверки допустимости автоматических запросов.
- Реальная работа с документами возможна лишь в отдельном pilot-окружении после security/privacy review.

### 2.4 Ограничения

- Команда — два разработчика; срок — апрель 2027.
- MVP развёртывается через Docker Compose без Kubernetes и Kafka.
- Документы не передаются внешнему AI API.
- Испания и Япония в MVP имеют capability `officialLink`; monitoring для них не реализуется.
- Деградация внешнего портала не должна блокировать checklist, документы и напоминания.

## 3. Требования

Формулировка функциональных требований — «система должна»; каждое требование имеет наблюдаемый критерий приёмки.

### 3.1 Доступ и согласия

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-001 | Система должна аутентифицировать Applicant по серверно проверенному `Telegram.WebApp.initData`. | Валидная подпись создаёт/открывает профиль и сессию; клиентские поля без проверки не принимаются. |
| FR-002 | Система должна отклонять невалидный или просроченный `initData`. | Сессия не создаётся; ответ не раскрывает секреты или детали проверки подписи. |
| FR-003 | Система должна разрешать административные операции только роли Administrator. | Applicant получает 403 для публикации правил, feature flags и health admin API. |
| FR-004 | Система должна получить актуальное согласие до загрузки документа. | Без согласия upload URL не выдаётся; после принятия сохранены версия, actor и timestamp. |

### 3.2 Заявка и checklist

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-005 | Система должна создавать draft-заявку для Италии, Испании или Японии. | Валидная форма создаёт заявку со статусом `draft`; иная страна отклоняется. |
| FR-006 | Система должна хранить страну, тип визы, цель, даты и город подачи. | Повторное чтение возвращает сохранённые значения; обязательные поля не могут быть пустыми. |
| FR-007 | Система должна позволять владельцу добавлять, изменять и удалять Family member до закрытия заявки. | CRUD доступен только владельцу и запрещён после закрытия заявки. |
| FR-008 | Система должна проверять обязательные поля и логическую согласованность дат. | Невалидная форма не сохраняется как готовая; каждое нарушение связано с полем и объяснено. |
| FR-009 | Система должна позволять Administrator создавать draft-версию ruleset. | Создание draft не изменяет checklist production-заявок. |
| FR-010 | Каждое правило должно хранить источник, дату проверки, условия применения и требуемое действие/документ. | Правило без обязательного metadata не проходит валидацию публикации. |
| FR-011 | Система должна использовать для новых checklist только опубликованный ruleset. | Draft/review версия не выбирается генератором; published версия после публикации immutable. |
| FR-012 | Заявка должна ссылаться на конкретный `ruleset_id`. | Повторное открытие checklist использует прежнюю версию до явного пересчёта владельцем. |
| FR-013 | Система должна генерировать checklist по параметрам заявки и каждого участника. | Эталонный кейс создаёт ожидаемые общие и личные пункты без лишних дублей. |
| FR-014 | Владелец должен иметь возможность менять статус доступного пункта checklist. | Изменение сохраняется, пересчитывает прогресс и недоступно пользователю чужой заявки. |

### 3.3 Документы и проверки

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-015 | Система должна выдавать временный signed URL для разрешённого файла и заявки владельца. | URL действует только для одной операции/объекта, истекает по TTL и не даёт доступа к чужому объекту. |
| FR-016 | Загруженный файл должен пройти проверки типа, размера и вредоносного содержимого до OCR. | Неподдерживаемый или опасный файл изолируется; OCR job не создаётся. |
| FR-017 | OCR-worker должен локально извлекать поддерживаемые поля и confidence. | Для эталонного файла сохранены поля, confidence и версия распознавателя; внешний AI API не вызывается. |
| FR-018 | Applicant должен подтвердить или исправить распознанные поля до итоговой проверки. | До подтверждения итоговые проверки не запускаются; после подтверждения используются исправленные значения. |
| FR-019 | Система должна проверять обязательные поля, даты и согласованность данных между документами. | На размеченном наборе каждый ожидаемый check имеет один из статусов `critical`, `warning`, `passed`, `not_checked`. |
| FR-020 | Каждое несоответствие должно иметь уровень, объяснение, `rule_id` и `source_id`. | Результат без любого из обязательных атрибутов не показывается как завершённый; гарантия решения не формулируется. |
| FR-021 | Applicant должен иметь возможность удалить исходный файл и производные OCR-данные. | После завершения идемпотентной deletion job объект и поля недоступны; audit не содержит содержимое документа. |

### 3.4 Сроки и уведомления

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-022 | Система должна рассчитывать сроки из дат поездки и ruleset. | Для эталонной заявки рассчитанные deadline совпадают с ожидаемыми и сохраняют `rule_id`. |
| FR-023 | Applicant должен иметь возможность включать и отключать некритичные Telegram-напоминания. | Изменение настройки применяется к будущим некритичным отправкам и не меняет checklist. |
| FR-024 | Worker должен повторять временно неуспешную доставку без дублирования одного уведомления. | Retry ограничен; один idempotency key приводит максимум к одному пользовательскому сообщению. |

### 3.5 Запись и слоты

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-025 | Система должна хранить capability-флаги каждого country adapter. | Конфигурация явно различает `officialLink`, `slotMonitoring` и `unsupported`. |
| FR-026 | Для каждой поддерживаемой страны система должна показывать проверенный официальный URL записи. | Италия, Испания и Япония открывают URL из опубликованного источника; ссылка имеет дату проверки. |
| FR-027 | Мониторинг должен запускаться только при capability, feature flag и здоровом адаптере. | При невыполнении любого условия внешняя задача не стартует. |
| FR-028 | Adapter не должен обходить CAPTCHA/авторизацию, создавать аккаунт или бронировать слот. | Контрактные тесты и журнал запросов не содержат таких действий; при появлении защиты выполнение прекращается. |
| FR-029 | При неизвестной структуре, 403/429, CAPTCHA или серии timeout adapter должен открыть circuit breaker и создать alert. | Новые проверки остановлены; Administrator видит причину и последнюю успешную проверку. |
| FR-030 | При новой доступности система должна отправить одно уведомление с официальной ссылкой. | Повтор одного состояния не создаёт сообщение; изменение состояния создаёт не более одного события. |

### 3.6 Администрирование, аудит и retention

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-031 | Administrator должен видеть health workers/adapters без содержимого документов по умолчанию. | Экран показывает status, error class и timestamps, но не паспортные поля или исходные имена файлов. |
| FR-032 | Публикация правил, изменение ролей, доступ к документу и удаление данных должны записываться в audit log. | Запись содержит actor, action, target, timestamp и request ID; чувствительные поля отсутствуют. |
| FR-033 | Закрытие заявки должно планировать удаление исходных файлов через 30 дней. | После 30 дней retention job удаляет объект и производные данные; повторный запуск безопасен. |
| FR-034 | По запросу Applicant исходные файлы должны удаляться до истечения 30 дней. | Владелец может запустить немедленное удаление; другой пользователь получает отказ. |
### 3.7 Тестовая оплата

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-035 | Доступ к тарифу должен определяться через интерфейс `PaymentProvider`. | Domain service работает с TestPaymentProvider без зависимости от конкретного эквайринга. |
| FR-036 | MVP должен использовать TestPaymentProvider без приёма денег и платёжных реквизитов. | Успешный сценарий создаёт `paid_test`; запрос реквизитов и внешнее списание отсутствуют. |
| FR-037 | Повторный payment callback должен обрабатываться идемпотентно. | Два callback с одним provider event ID создают один переход заказа и один доступ. |

### 3.8 Источники требований

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-038 | Система должна сохранять snapshot/checksum источника и показывать Administrator diff до публикации. | Изменение источника создаёт draft/diff, но не меняет production ruleset автоматически. |

### 3.9 Нефункциональные требования

| ID | Категория | Требование и критерий приёмки |
|---|---|---|
| NFR-001 | Производительность | 95% обычных API-запросов завершаются ≤ 2 с при согласованном пилотном профиле нагрузки; подтверждается load test. |
| NFR-002 | Доступность | Целевая доступность MVP ≥ 99% в месяц без согласованных работ; измеряется внешним health check. |
| NFR-003 | Безопасность транспорта | Все внешние соединения используют TLS; HTTP перенаправляется или отклоняется. |
| NFR-004 | Шифрование | Object storage и backup используют encryption at rest; настройка подтверждена инфраструктурным тестом/review. |
| NFR-005 | Контроль файлов | Signed URL ограничен объектом, операцией и TTL; просроченный URL даёт отказ. |
| NFR-006 | Приватность логов | Паспортные данные, исходные имена файлов и полный OCR не попадают в logs/traces/metrics; проверяется log scan. |
| NFR-007 | Локальная обработка | OCR и rule validation выполняются на инфраструктуре VisaFlow без передачи документа внешнему AI API. |
| NFR-008 | Аудируемость | Audit event содержит actor, action, target, timestamp и request ID и доступен только Administrator. |
| NFR-009 | Надёжность jobs | Фоновые задачи идемпотентны, имеют timeout, ограниченный retry и dead-letter/failed status. |
| NFR-010 | Восстановление | PostgreSQL и storage резервируются; успешное восстановление тестового окружения выполнено до пилота. |
| NFR-011 | Сопровождаемость | Каждый визовый портал скрыт за `AppointmentProvider`; отказ одного adapter не нарушает core-сценарии. |
| NFR-012 | Доступность интерфейса | Ключевые сценарии доступны с клавиатуры, имеют видимый focus и текстовые labels; проходят ручной accessibility checklist. |

### 3.10 Бизнес-правила

| ID | Правило |
|---|---|
| BR-001 | MVP обрабатывает только туристические визы поддерживаемых стран. |
| BR-002 | Новая версия ruleset не изменяет созданный checklist без явного пересчёта владельцем. |
| BR-003 | Результаты проверки: `critical`, `warning`, `passed`, `not_checked`. |
| BR-004 | `passed` не означает гарантию выдачи визы. |
| BR-005 | Полная автозапись и обход CAPTCHA/антибот-защиты запрещены. |
| BR-006 | В development, CI и учебной демонстрации используются только синтетические документы. |
| BR-007 | Реальный документ допускается только в отдельно разрешённом pilot-окружении. |

### 3.11 Внешние интерфейсы

- **Telegram Mini Apps:** получение и серверная валидация `initData` для FR-001/FR-002.
- **Telegram Bot API:** отправка напоминаний и slot notification для FR-024/FR-030.
- **S3-compatible storage:** signed upload/read/delete для FR-015/FR-021/FR-033/FR-034.
- **Официальные источники:** snapshot/checksum/diff и проверенные URL для FR-026/FR-038.
- **Italy VMS adapter:** только разрешённая проверка доступности для FR-027–FR-030.
- **TestPaymentProvider:** тестовый payment flow для FR-035–FR-037.
